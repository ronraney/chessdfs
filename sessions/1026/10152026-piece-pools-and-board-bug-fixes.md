### 1. Click-to-move investigation (commit `934bf2a`)

Bug report: click-select then click-destination on the build board did nothing (dots appeared, then vanished); dragging worked. Investigated by calling chessground's own public `selectSquare()` twice — exactly what a real click does internally (`board.selectSquare` → `board.userMove`) — against the **real, unmocked** chessground library in `BuildBoard.test.tsx` (new file) and a parallel suite in `BuildScreen.test.tsx`. Both passed cleanly, including across a re-render with a freshly-built `dests` Map (the scenario BuildScreen actually produces every render, since `dests` is rebuilt inline, not memoized). This disproved both of the task's own hypotheses ("chessground reconfigured on re-render, resetting selection" and "the move handler only fires for drags") — the shared `movable.events.after` path fires identically for click and drag.

Tried to get a real browser running to test an actual click (not just the library's own API): Playwright's cached Chromium (`~/.cache/ms-playwright/chromium_headless_shell-1248`) is present on this machine but fails to launch — `libasound.so.2` missing, no sudo to install it. Did not attempt to work around that (installing/faking system libraries would cross into "work around a blocker" territory CLAUDE.md says not to do). No code-level cause was found this way.

Delivered the independently-specified part of the task regardless: `index.css` gained a `--board-marker` token per theme (Club's own `--accent` only clears ~2.3:1 against `--board-dark`, below the 3:1 floor; a darker red clears ~3.5:1+) and `.move-dest`/`.oc.move-dest`/`.selected` now render as solid theme-accent dots/rings/an outline instead of brown.css's fixed, low-contrast green.

### 2. White's second move silently failing (commit `290ce91`)

Follow-up bug report, and the answer to investigation #1's open question: after Black's first reply, White couldn't make *any* second move — drag and click both snapped back silently, every piece, every time, no console errors. This is the same click/drag-share-one-path mechanism from #1, but the actual root cause: chessground's own `state.turnColor` only toggles inside its own move functions (`board.baseMove`/`baseUserMove`), run when White moves via the board. Black's reply lands as a plain `fen` prop update instead (`fen.js`'s `read()` only parses piece placement, never the side-to-move field), so nothing ever told chessground it was White's turn again — `turnColor` stuck at `'black'` forever after White's first move. White's own pieces then failed `isMovable` (`movable.color !== turnColor`), but `isPremovable` (the *opposite* check) started passing instead, since `premovable.enabled` defaults to `true`: selecting a piece still showed dots (premove destinations, not `movable.dests`), and completing one called `board.setPremove` — recorded, never executed, never reported — instead of `movable.events.after`. Affected every White move after the first, regardless of commit type (ordinary, castle, capture, Take back), since all of them toggle `turnColor` the same way.

Fix in `BuildBoard.tsx`: pass `turnColor: "white"` on every update (not just at mount), plus `premovable: { enabled: false }` as belt-and-suspenders (this app has no use for premoves; any future regression here now fails loudly — nothing selectable — instead of silently eating a move).

New test file `BuildScreen.secondMove.test.tsx` drives the real, unmocked chessground library through the full move/pick/lock/Black-replies/second-move cycle, plus after Take back, after castling, and after a capture — confirmed failing against the unfixed code first (per the task's explicit ask), then passing after the fix. Also fixed a separate, smaller issue the task called out: `handleBoardMove`'s old silent `return` on an unmatched `(orig, dest)` now sets a status-line message instead (`"<orig>-<dest> isn't a legal move right now."`), cleared on the next attempt or Take back.

### 3. Piece pools rule change (commit `f2ff2fc`)

Large rule change: replaced first-match-wins classification with pools — a player belongs to every piece band they qualify for, not just the first match. `classify()` in both `dfs_chess/pieces.py` and `web/src/engine/pieces.ts` now returns a set (`frozenset[Piece]` / `ReadonlySet<Piece>`), not one `Piece`.

New NFL bands (`config/sports/nfl.json`): King unchanged (any QB). Queen now explicitly excludes QB via a **new `exclude_positions` band field** (pools no longer rely on band order to keep King exclusive) rather than an enumerated position allow-list — tried the allow-list first, but existing tests use synthetic positions like `"FB"` with no roster slot at all, which an allow-list would silently leave unclassified; `exclude_positions` lets "any non-QB" stay genuinely open-ended. Rook/Bishop/Knight lost their $7,000 ceiling (so a $7,000+ RB/WR/TE is in both its position band and Queen now) and Knight's floor moved from $4,500 to $5,000 (later reverted, see below). Pawn became two bands: any non-QB under $5,000, plus all DST at any salary.

Config validation changed from "requires one literal catch-all band" to a merged-interval check in `load_sport_config`/`loadSportConfig`: walks every real roster position (QB/RB/WR/TE/DST) and rejects the config if any position has a salary gap no band covers.

Audited and converted every `classify(...) is/===` comparison to pool-membership (`piece in classify(...)` / `.has(piece)`) across `rules.py`/`.ts`, `build.py`/`.ts`, `cli.py`, `tools/sim_builds.py`, `SetupScreen.tsx`, `buildStats.ts`. Found and fixed the one real "one piece per player" design question the task flagged in advance: `apply_capture_move`'s transfer branch used to set the transferred `Move`'s piece via a fresh `classify(captured, sport)` call — harmless when single-valued, ambiguous once a player can have multiple pools. Fixed by looking up the piece that actually locked the player (their existing `Move.piece`, searched across both sides' move lists) instead of re-deriving it — "a player's piece is the piece that locked them," per the task's own resolution. Confirmed by code audit this was the *only* such spot; every other display/capture path already read `Move.piece` (set once, at lock time, from the real chess board), never re-derived.

Also found, while auditing, a real adjacent bug: `openings.py`'s `_piece_eligible_positions` (backing `legal_depth`/`opening_preview`) wasn't subtracting `exclude_positions`, so Queen/Pawn's proxy eligibility for roster-feasibility estimation incorrectly included QB. Fixed in both languages; did not add a dedicated new test for it (constructing a clean minimal repro was disproportionate effort for a narrow estimation-only edge case — flagged in the commit message instead).

`tools/export_parity.py` regenerated: `classify_all_players` now exports each player's full pool (sorted list) instead of one piece; added two new scenarios for a $7,000+ RB picked via a real Rook move and, separately, a real Queen move. `parity.test.ts` updated to match; all 43 scenarios pass.

New boundary tests in `test_pieces.py`/`pieces.test.ts` ($4,999 vs $5,000 for RB/WR/TE; $6,999 vs $7,000 Rook/Bishop/Knight-vs-Queen overlap; DST's always-Pawn-eligible rule). Every existing fixture with a sub-$5,000 TE relying on the old $4,500 Knight floor got bumped to $5,200+ across `test_rules.py`, `test_build.py`, `test_cli.py`, `buildFlow.test.ts`, `rules.test.ts`, `build.test.ts` — none of them were testing the boundary itself, just needed "a generic Knight-eligible TE." Left a handful of hand-built/lineup-only fixtures at the old $4,600 literal deliberately (they never call `classify()` — a hand-built `Move` record or a pure `lineup_still_completable` sum doesn't care). `BuildScreen.test.tsx`'s `selectTopRow` test helper needed hardening to skip infeasible rows: with far more Pawn-pool candidates sharing the real sample data now, the single top-projection candidate is more often one Black's own replies already spoke for a roster slot for — this surfaced as a real test failure (`capturing an unmoved piece opens the modal for that piece type`), traced via temporary debug logging to a disabled "Lock player" button, not a classification bug.

Result: 324 Vitest passing, 186 pytest passing (both confirmed clean with an extended test timeout — see Environment note below), `tsc -b`/`oxlint`/`npm run build` all clean.

### 4. Knight pool floor reverted to $4,500 (commit `1d2dcb8`)
